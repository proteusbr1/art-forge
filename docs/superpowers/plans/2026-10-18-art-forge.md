# art-forge: implementation plan

> **For agentic workers:** use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans, task by task. Steps use checkboxes (`- [ ]`). This plan
> holds no code by the maintainer's choice: each task gives files, contracts, behaviours
> to test and how to verify; code is written during execution. Source files from the
> author's earlier private projects are located through a local, unversioned source map
> (`local/private/sources.md`).

**Goal:** the factory ready to take orders from any game, including the new end-to-end
`humanoid` recipe, verified dry (no GPU inference).

**Architecture:** the factory core from the author's earlier factory, extended with
per-piece order keys, a per-stage option catalogue, an exclusive group for local GPU
stages, and local tools: a rig runner (SkinTokens by default, UniRig as option), a
humanoid exporter (Blender), a bone renamer to Godot's humanoid profile and a review sheet
rendered by Godot off-screen.

**Tech stack:** system Python 3 with NumPy and Pillow (factory); `bpy` 4.2 (exporter);
SkinTokens (rig; UniRig optional); Godot 4 standard edition with GDScript (sheet); Windows PowerShell 5.1
(launcher); local ComfyUI through its HTTP API only.

Design: `docs/superpowers/specs/2026-10-18-art-forge-design.md`.

## Global constraints

- No game names, briefs, prompts, images or outputs in the repository; examples and tests
  use generic subjects.
- Code, identifiers, script names and parameters in English; PowerShell compatible with
  5.1 and ASCII only.
- Local ComfyUI through its HTTP API only; workflows with paid API nodes refused on load.
- Media, weights, outputs and `forge.local.json` outside git.
- No GPU inference during this plan. Tests that need local tools (Blender, Godot,
  SkinTokens, UniRig)
  are skipped when the configuration does not point to them.
- Silent tests with no visible window: Godot with audio off and its window at
  (-20000, -20000).

### Task 2: Humanoid local tools (exporter, bones, sheet)

**Files:** create `tools/blender/humanoid_bones.py`, `tools/blender/humanoid_export.py`,
`tools/review_godot/` (project, scene and script), `forge/local_gpu.py` (the tool runners),
`docs/conventions.md`, `tests/fixtures/` (synthetic skeleton, item and library plus their
generator), `tests/test_humanoid_bones.py`, `tests/test_local_tools_smoke.py`.

**Contracts:**
- `humanoid_bones.py`: `bone_roles(armature)` → bone → role, found from the tree (root =
  hips; the chain going up = spine, the top's highest child = neck and head, the other two
  = arms; the root's other children = legs; left from where the toes point), and
  `godot_name(role)` → the `SkeletonProfileHumanoid` name (Hips, Spine, Chest,
  UpperChest, Neck, Head, LeftShoulder, LeftUpperArm, LeftLowerArm, LeftHand,
  LeftUpperLeg, LeftLowerLeg, LeftFoot, LeftToes and the Right equivalents). Bones without
  a role keep their original names. A pure part (no `bpy`, over a tree of points) is
  testable with the system Python.
- `humanoid_export.py` (runs in `blender_python`): `--rig <rigged glb>`, `--out <folder>`,
  `--name`, `--tris`, `--tex`, `--height` (metres), `--head`, `--hands`, `--feet`,
  `--widen` (default 1.0), `--clips <library json>` (optional), `--items <held items
  folder>` (optional), `--glow` with `--glow-hues` (optional). Writes `<name>.glb` with
  renamed bones, retargeted animations (rest pose only without `--clips`), a normal map
  baked from the full mesh, the painted texture at its original size; `model.json`;
  `regions_mask.png` (red skin, green hair, blue glow). A generic port of the earlier
  exporter without game-specific recolouring, level heights, per-tile phases or
  unit-specific options (those become motion-library fields or go away).
- `docs/conventions.md` documents `model.json` (keys in English), the motion library
  (canonical joints in body coordinates, what each pose holds, how the feet stand) and the
  held-item socket file.
- `tools/review_godot/`: command line with a list of GLBs (or failure marks), camera
  (`pitch` in degrees, list of `yaws`, figure height in pixels, orthographic), animation to
  show (default the first idle, else the rest pose) and PNG output. Each variant appears
  in every small direction plus one large front view, labelled by the script. Window off
  screen, audio off, exits by itself.
- `forge/local_gpu.py`: `run_rig(mesh, out, config, seed, method)` with `method`
  `skintokens` (default) or `unirig`, `run_export(rig, out, config,
  params, clips, items)`, `run_review(glbs, out, config, camera)`; each runs the external
  process, keeps `stdout`/`stderr` next to the output and returns the produced files or
  raises an error naming the log.

  bones in the rig tools' hierarchy (SkinTokens style: `bone_N` plus five-finger chains
  per hand), a "box" item with its socket file, and a library with an
  idle pose and an 8-frame step. The GLBs are generated by `blender_python` on the first

- [ ] **Step 2:** tests of the pure part of `humanoid_bones.py`: correct roles on a

  (which keep their names) and on a tree with finger chains under each hand (fingers keep

- [ ] **Step 3:** port the exporter as described, with the renamer. Smoke test (skipped
  without `blender_python`): export the synthetic humanoid with and without a library;
  re-import the GLB in a new process and check humanoid-profile bone names, animations
  present with the library's duration, height equal to `--height` within 1 cm, texture
  and normal map present, hands within 2 cm of the box's sockets in holding poses.
- [ ] **Step 4:** the Godot sheet project and `run_review`. Smoke test (skipped without
  `godot`): sheet of two variants and one failure; check image size, that every figure

- [ ] **Step 5:** `run_rig`: `skintokens` runs the configured SkinTokens checkout with its
  own Python (skeleton and weights transferred onto the given mesh, fixed seed, beam
  count as a parameter, no window); `unirig` runs UniRig's python steps (extract,
  skeleton, extract, skin, merge). No automatic test in this task (they use the GPU);
  `check_order` checks the paths of the chosen method.
- [ ] **Step 6:** smoke test with a real existing rig, no inference: run export and sheet on
  a rigged GLB given by the `FORGE_SMOKE_RIG` environment variable and a real motion
  library given by `FORGE_SMOKE_CLIPS` (never copied into the repository). Keep the sheet
  in `local/smoke/` and look at the image. Export the smoke provenance with
  `--provenance` and check it lists rig, library, tools and hashes. Write
  `docs/conventions.md`. Commit.

**Amendment A (external review, applies to this task):**
- **Explicit, validated bone map.** `humanoid_bones.propose_bone_map(armature)` → a map
  role → bone name plus a validation report, written as `bone_map.json` next to the rig.
  Hips = the first bone whose subtree branches into two legs and a spine (extra root bones
  above it are allowed and kept). Validation: exactly one hips; a spine chain of at least
  two bones; two arms with shoulder (optional), upper arm, lower arm and hand; two legs
  with upper leg, lower leg and foot (toes optional); left/right decided from the rest
  geometry and checked for consistency between hands and feet; segment lengths of the two
  sides within 15 % of each other. Correction: a map given by the order
  (`inputs.bone_map`) or a `bone_map.json` in the output marked `"manual": true` wins over
  the proposal. An invalid map stops the export with the report; the exporter never
  guesses. Renaming alone is not accepted as proof of transfer (see the motion report).
- **Mesh files through the stages.** The exporter receives the painted game mesh (already
  reduced by the mesh stage) and a separate `--bake-source` (the raw high-resolution mesh
  from the mesh stage, before reduction). It does not reduce again unless the mesh is above
  `--tris` (then it reduces and says so in the report). After any reduction or weight
  change it validates and writes `mesh_report.json`: UV layer present, one material with a
  base-colour texture, every vertex weighted, weights normalised, maximum influences per
  vertex, triangle count.
- **Motion report.** With `--clips`, the exporter plays every clip on the exported
  armature and writes `motion_report.json`: per clip, foot slide in centimetres during the
  stance frames the library declares; hand-to-socket distance in holding poses; IK reach
  shortfall in centimetres (target beyond the arm's reach); body deformation as the 95th
  percentile of edge stretch against the rest pose; a held-item penetration proxy (depth
  of the item's box inside the body surface). Each measure has a default threshold
  (parameters) and the report lists the clips over threshold as flags. Start and stop
  clips, when the library has them, are measured like the others.
- **Review shows motion and flags.** The sheet adds, per variant, an animated strip (8
  frames of the walk, plus start and stop if present) from the review camera, and prints
  the motion and mesh flags under each variant. Every candidate is labelled pending review;
  nothing in the sheet or reports calls a candidate approved.
- [ ] **Step 7:** tests for the bone map: hips found under an extra root bone; mirrored rig;
  rig with fingers; an invalid rig (one arm missing) gives a report and no map; a manual
  map wins. Smoke (skipped without `blender_python`): export of the synthetic humanoid
  writes `bone_map.json`, `mesh_report.json` and `motion_report.json`; a deliberately bad
  clip (feet moving during declared stance) is flagged; the synthetic export with
  `--bake-source` bakes from the high mesh without reducing the game mesh. Re-run the
  real-rig smoke and look at the sheet with the strip and flags. Commit and push.

**Verification:** tests pass (smoke tests run on a machine whose configuration points to
Blender, Godot and UniRig); the real-rig sheet shows the character from above and from
the front, animated in its idle pose, with no visible window during the run.

### Task 3: Stage settings, effective parameters, readiness check, GPU coordination

**Files:** modify `forge/stages.py`, `forge/order.py`, `forge/factory_core.py`,
`forge/comfy_jobs.py`, `forge/provenance.py`, `forge/config.py`, `Run-Forge.ps1`,
`docs/order.md`; create `forge/gpu_lock.py`, `forge/readiness.py`,
`tests/test_stage_settings.py`, `tests/test_readiness.py`, `tests/test_gpu_coordination.py`.

**Contracts:**
- **Per-stage settings.** A `stages` entry is either an option name or an object
  `{"option": <name>, "settings": {<setting>: <value>}}`. Each option in the catalogue
  declares its named settings, their types and ranges and where each lands
  (`<node>.<input>` of its workflow, or an argument of its tool). Sampler-bearing options
  declare one steps setting per sampler (TRELLIS.2: structure, shape, upsample and texture
  samplers each get their own steps and seed), plus resolution, sampler, scheduler and
  guidance where the workflow has them. `check_order` rejects unknown settings and
  out-of-range values. Settings enter the job specification (hash) like any value.
- **Effective parameters.** After each ComfyUI job the factory reads the executed prompt
  back from `/history` and records, per node, the inputs actually submitted; after each
  local tool, the arguments actually passed. The catalogue marks inputs known to be
  ignored or overridden by an implementation (for example a Paint wrapper that fixes its
  noise seed) and the record keeps both `requested` and `effective` (`effective` is
  `null` with a reason when unknown). Provenance export includes these records.
- **Readiness check, two levels.** `forge.readiness.check_environment(order, config,
  server)` is separate from `check_order`. `-Check` prints two results: "order valid" or
  its problems; and the environment as `verified`, `not ready` (with the list) or `not
  verified` (server unreachable: local validation done, environment not checked; never
  reported as ready). The environment check covers: node classes present; every model
  file a workflow names is in the corresponding loader's option list from `/object_info`;
  local tools present with their weight files (SkinTokens checkpoints, UniRig weights);
  Blender and Godot versions recorded.
- **GPU coordination.** `forge.gpu_lock` holds a machine-wide lock file (under the user's
  local application data folder) taken by a factory run for the whole run and by each
  local GPU job, so two factory instances never share the card. Before a `local_gpu` job:
  the whole ComfyUI queue must be empty, from any client (`queue_running` and
  `queue_pending`), then `/free`; other processes on the card are listed from
  `nvidia-smi` and logged (the job waits up to a configurable time while another process
  holds more than a configurable amount of VRAM, then goes). While a `local_gpu` job runs
  the factory sends nothing. If an external generation starts meanwhile and the job fails,
  it is retried once after the queue is empty again; the log names the cause when it is
  an out-of-memory error.

- [ ] **Step 1:** tests of settings: string and object forms; per-sampler steps reach the
  right nodes; unknown setting and out-of-range value reported; changing one setting
  changes only that job's hash and its dependants'. Run: fail. Implement. Run: pass.
- [ ] **Step 2:** tests of effective parameters with the fake server (it returns a
  `/history` whose prompt differs from what was requested for one input, and an input
  marked ignored): the record holds `requested` and `effective`; provenance export
  includes them. Run: fail. Implement. Run: pass.
- [ ] **Step 3:** tests of readiness with a fake `/object_info`: missing node class,

- [ ] **Step 4:** tests of coordination with the fake server: a second factory instance

### Task 4: The `humanoid` recipe in the queue and sample order

**Files:** modify `forge/recipes.py`, `forge/stages.py`, `forge/local_steps.py`,
`forge/local_gpu.py`, `README.md`, `docs/order.md`; create `tests/test_humanoid_recipe.py`,
`tests/fixtures/order_humanoid.json`.

**Contracts:**
- `stages.py` defines for `humanoid` the stages `reference`, `pose`, `cutout`, `mesh`,
  `paint`, `rig`, `export`, `review`, with defaults and options: `reference` =
  `qwen21_base` (default), `qwen21_turbo`, `klein`, `input_image`; `pose` =
  `qwen_edit_2511` (default; corrects A-pose, open hands apart, full body, nothing held);
  `cutout` = `birefnet` (default), `qwen_edit_character`; `mesh` = `trellis2` (default),
  `hunyuan21`; `paint` = `hunyuan_paint` (default), `trellis2_texture`; `rig` =
  `skintokens` (default), `unirig`; `export` = `humanoid_export`; `review` =
  `godot_sheet`. Each option declares its workflow or tool, group, heaviness, output
  roles, the `params` it reads and its named settings (Task 3). `skip` accepts `pose`,
  `paint` (TRELLIS.2's texture stays), `rig` and `export` (statue: the sheet shows the
  painted mesh).
- The mesh stage outputs two roles: `raw_mesh` (before reduction, the bake source) and
  `game_mesh` (reduced to `params.tris`); paint works on `game_mesh` and outputs
  `painted_mesh`; export receives `painted_mesh` and `raw_mesh` as `--bake-source`.
- `recipe_humanoid(fam, a, st)` makes, for each seed of `seeds_for(family/piece,
  variants)`, the chain of jobs with ids `<family>/<piece>/v<seed>/<stage>`, then one
  piece `review` job (all variants, with their motion and mesh reports) and one `final`
  job. Reference prompt: `brief`, tier, family style, `global` and the `view_humanoid`
  view (required in `style` when an order has a humanoid; it describes A-pose, empty hands
  away from the body, full body, grey background). The bone map flow of Task 2 is used:
  an invalid proposed map fails that variant's export with the report.
- New job kinds: `local_gpu` (runs `run_rig`, `run_export` or `run_review`, under Task 3's
  coordination) and `final` (local; copies the chosen variant to `final/`; the pick uses
  the core's manual pick mechanism; the automatic pick is provisional: the first variant
  that finished every stage with no motion or mesh flag, else the first that finished,
  always marked pending review).
- The estimate gains times for `trellis2`, `hunyuan_paint`, `qwen21_base`, `qwen_edit`
  and `local_gpu` (initial values from earlier measurements, marked as estimates).
- Folder inputs (for example `inputs.items`) enter the specification hash by the hashes
  of the files inside them (sorted relative paths and contents).
- A failed variant does not block the others; `review` runs with the variants that
  finished and marks the failures; `final` waits for at least one complete variant.
